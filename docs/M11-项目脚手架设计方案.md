# lui M11 设计方案：项目脚手架与工具链（开发 / 测试 / 打包 / 交付）

> 状态：已实施（2026-09-14）。基线：M10 完成（runtests 649 项全绿）。
> 本文给出 `lui-render --init` 的定位、约束、设计与实施记录。
>
> **M12 取代说明（2026-09-17）**：脚手架升级为应用脚手架（`lui init`），生成物以
> `lui.json` 应用清单为核心，`run-*.cmd` 改为调用运行时命令面（`lui dev/build/pack/check`）
> 而不再硬编码入口与视口；`--init/--check/--pack` 旧参数仍可用。本文第 3 章的目录布局、
> 清单字段与脚本内容已被取代，机制类结论（模板定位三态链、只写不改不删、`.cmd` 纯 ASCII、
> 退出码即门禁）仍然有效。见《M12-Electron式运行时重设计方案.md》§9。

---

## 1. 背景与问题

M9 把渲染器做成了"能出图、能分发"的通用工具，但一个用户拿到 `lui-render.exe` 之后，
**从零到能跑的工程**这一段是断的：

| 断点 | 现状 | 后果 |
| --- | --- | --- |
| 没有工程骨架 | 只有 `demo/` 里的演示页可参考 | 新用户不知道该建哪些文件、怎么摆目录 |
| 组件库是外部的 | 组件库在 lui 仓库的 `ui/`，页面用 `../ui/index.ts` 引用 | 拷走渲染器还是跑不出组件；必须连仓库一起搬 |
| 没有"页面能跑"的判定 | 只能出图看，脚本报错只在 stderr 里飘 | 改坏脚本无法在 CI 里挡住 |
| 没有交付路径 | `npm run pack` 是**框架自己**的打包脚本 | 用户对自己的应用没有等价的"打包成交付目录"能力 |

一句话：M9 交付了"工具"，M11 要补齐"用这个工具做一个项目"的整条路。

---

## 2. 目标与非目标

**目标**

1. `--init <目录>` 一条命令产出**可立即开发**的工程：页面 / 脚本 / 双主题样式 / 自带组件库运行时 / 三支脚本 / 清单 / README。
2. 生成物覆盖完整生命周期：**开发**（预览热重载）→ **测试**（CI 可判定的自检 + 出图）→ **打包**（交付目录）→ **交付**（自包含、可拷走）。
3. 生成即自包含：不依赖 lui 仓库、不依赖 Node。单程序版 `lui-render-single.exe` 也要能 `--init`。
4. 补齐渲染器的两个工具链缺口：`--check`（脚本自检，退出码可判定）与 `--pack`（用户侧交付目录）。

**非目标**

- 不做包管理器 / 依赖解析 / 构建系统（零依赖是 lui 的立身之本，工程也不需要 npm）
- 不做跨平台工程脚本（`.sh`）：当前渲染器一等公民是 Windows；脚本模板先只给 `.cmd`，POSIX 需要时再补
- 不做工程模板的参数化定制（多套模板）：一套起步页足够，改起来就是改自己的文件
- 不做 IDE 集成 / 调试器接入

## 3. 设计

### 3.1 模板即真文件（`scaffold/` 目录）

**决策**：模板是仓库里的真目录 `scaffold/`，不是 Pascal 源码里的字符串字面量。

理由：

- 模板可读、可 diff、可被测试**直接渲染**（runtests 里就渲染它）
- 改模板不需要改 Pascal、不需要重新编译渲染器（打包分发时随包拷 `scaffold/`）
- 单程序版把它内嵌进 exe（`embed.js` 收 `scaffold/`），两种分发形态共用同一份模板

占位符用 `@@KEY@@` 形式（不与 XML/CSS/TS 的任何合法语法冲突）：

| 占位符 | 值 | 用在哪 |
| --- | --- | --- |
| `@@PROJECT_NAME@@` | `--name` 或目标目录名 | 页面 title、注释、README |
| `@@LUI_VERSION@@` / `@@PROJECT_VERSION@@` / `@@DATE@@` | 渲染器版本 / 模板版本 / 生成日期 | 清单、README |
| `@@RENDERER@@` | 渲染器绝对路径（**原生**分隔符） | `.cmd` 脚本 |
| `@@RENDERER_POSIX@@` | 同上（**正斜杠**） | `lui-project.json`（JSON 里 `\` 是转义符） |
| `@@WIDTH@@` / `@@HEIGHT@@` / `@@THEME@@` | 视口与主题 | 页面 window 属性、脚本命令、清单 |
| `@@DEV_THEME@@` | 预览用主题（`both` → `light`） | `run-dev.cmd`（预览窗一次只显示一档） |

### 3.2 工程布局与"自带运行时"

```
<项目>/
  src/main.xml            入口页面（结构 + x-* 绑定）
  src/main.ts             页面逻辑（reactive/computed/函数）
  src/main-light.css      浅色（完整样式表）
  src/main-dark.css       深色（完整样式表）
  ui/                     组件库运行时——从模板同级 ui/ 整树复制（53 个文件）
  run-dev.cmd             run-test.cmd             run-pack.cmd
  lui-project.json        工程清单
  README.md               工程说明（含引擎不支持清单，避免踩坑）
  .gitignore
  out/  dist/             渲染 / 交付产物（gitignore）
```

**关键点：`ui/` 是复制进来的，不是引用的**（ADR 42）。这样"生成即自包含"：工程可以脱离
lui 仓库单独存在、单独提交、单独交付。代价是每个工程带一份约 100 KB 的运行时 —— 值得。

模板里的 `.gitignore` 源文件名为 `gitignore`（无点），生成时还原为 `.gitignore`：否则
仓库里的 git 会把 `scaffold/.gitignore` 的内容当成忽略规则，作用到 `scaffold/` 子树
（模板文件会被静默忽略、不入库）。

### 3.3 三支脚本 = 四个阶段

| 脚本 | 阶段 | 底层命令 | 要点 |
| --- | --- | --- | --- |
| `run-dev.cmd` | 开发 | `lui-render src\main.xml -t light --watch` | 改 xml/css/ts 自动重载；F5/T/Esc |
| `run-test.cmd` | 测试 | `--check` 逐页 + `-O out -t both --json` | **任一页脚本报错 → 退出码 1**（CI 门禁） |
| `run-pack.cmd` | 打包 → 交付 | `--pack dist src\main.xml -t both --force` | 产出 `dist/`，整目录拷走即可运行 |

**为什么脚本是 ASCII-only**（重要，实测教训）：`cmd.exe` 按 **OEM 代码页**解码批处理文件，
不是 UTF-8。`.cmd` 里的中文注释在 GBK 控制台下乱码，更糟的是乱码字节会被当成命令去执行
（实测出现 `'瘧' 不是内部或外部命令`，并污染退出码）。因此 `.cmd` 模板全用英文注释，
**渲染器自身输出的中文不受影响**（那是 stdout，按控制台编码走，正常显示）。
runtests 有一条断言锁死 `.cmd` 必须是纯 ASCII。

### 3.4 `--check`：把"页面能跑"变成可判定的事

M9 的渲染只回答"能不能出图"。脚本报错会被引擎吞掉（按设计不崩应用），CI 无从判定。
`--check` 补上这一环：

- 完整装配（组件库 + 关联 CSS + 文档）→ 脚本执行 → 一次绘制（触发 `onMount` / 首轮绑定 / 布局）
- 收集 `TXuiScript.OnError` 全部阶段：编译 / 运行 / **未处理 Promise 拒绝** / I-O / 超预算
- 有错：打印逐条诊断（`文件(行,列) [阶段] 消息`），退出码 **1**；无错退出码 0
- `--json` 时汇总逐页结果到 stdout；`-v` 时把页面 `console.log` 也透出来作上下文
- 只跑一档主题（脚本错误与主题无关），`--theme both` 会归一为 light

### 3.5 `--pack`：用户侧的交付目录

与框架自己的 `npm run pack` 同构（便于共用文档与心智），但面向用户的工程：

```
dist/
  <renderer>.exe       渲染器副本（普通版或单程序版，取决于用哪个跑的）
  ui/                  组件库运行时
  pages/               页面及其关联资源（xml/css/ts/include/assets），相对引用原样成立
  preview-light.png    预览图（-t 决定一档或两档）
  preview-dark.png
  README.txt           交付说明（含具体命令行）
```

三个设计点：

1. **页面资源发现复用 `--add-page` 的那份规则**（同源函数 `CollectPageDeps`）：
   同名 `-<theme>.css` / `-<theme>.ts`、`nav-*.css`、`<include src>`、`<script src>`。
   规则只有一处实现，打包清单不会与运行时发现漂移（沿承 ADR 35）。
2. **路径解析三处同时成立**：`ui/` 与 `pages/` 是 exe 子目录（从 exe 目录向上能找到
   `ui/index.ts`）；`cd pages` 后运行 `..\exe`（从当前目录向上也能找到）；页面内引用
   全是 `pages/` 内的相对路径。实测：把 `dist/` 拷到别处、在 `pages/` 下运行渲染器出图成功。
3. **删除必须先被授权**：目标目录非空时需要 `--force` 才清空重建 —— 打包语义包含"重建"，
   但删除必须是用户显式要求的。

### 3.6 热重载修复（M9 遗留 P4）

M9 的预览窗只轮询**输入文件自身**的时间戳，改 CSS / `<script src>` 不触发重载，
而引擎早已具备依赖跟踪（`RecordDocSources` + `ReloadChangedFiles`）。M11 一并修掉：

- **GUI 预览**：`InitHost` 里开 `Engine.HotReload := FWatch`，删掉自建 `TTimer` 与
  `FLastMTime`（Timer 只保留"文档缺失时兜底"）。依赖变化即就地重载；仅 CSS 变化时
  保留 DOM 与运行时状态。
- **CLI `--watch`**：不再比对单个文件时间戳，改为轻量引擎实例装载一次后调
  `ReloadChangedFiles` 判定，命中才重跑整轮导出。

### 3.7 安全约束：只写不改不删

`--init` 绝不删用户文件：

| 目标目录状态 | 行为 |
| --- | --- |
| 不存在 | 创建并生成 |
| 是文件 | 报错退出 |
| 空目录 | 生成 |
| 非空且**有** `lui-project.json`（是 lui 工程） | 生成，**已存在文件默认跳过并保留**（便于日后重跑补齐新增文件） |
| 非空且**无**标记 | 拒绝，需 `--force`（避免误往任意目录铺文件） |

`--force` 只影响"是否覆盖同名文件"，任何情况下都不删除目标目录中的内容。

## 4. 实施中发现并修复的引擎缺陷

### 4.1 键控 `x-for` 移除条目后访问违例（严重）

**症状**：移除一个带 `transition` 的键控列表项后，**下一次 Draw 崩溃**（访问违例）。

**根因**：`xui_script_bind.ApplyForKeyed` 的移除路径自行
`Parent.RemoveChild(removed); removed.Free;`，绕过了引擎的瞬态引用复位。引擎持有若干
指向节点的弱引用（过渡动画表 `FTransitions`、悬停链 `FPointer`、指针捕捉 `FCaptureNode`），
节点被释放后这些引用悬垂；下一次 `Draw` 的 `FTransitions.Capture` 逐项读
`item.Node.Style` 即读到已释放内存。

**为什么一直没暴露**：`x-if` 是**摘除**（detach，不 free）所以安全；而此前没有任何用例
**移除**键控列表项（测试只做复用、重排、追加）。

**修复**：改走 `FEngine.RemoveElement`（内部先 `FPointer.Reset` / `FTransitions.Reset` /
清 `FCaptureNode`，再摘除、释放、置脏）—— 这是引擎既有的"运行时删节点正确入口"。

**锁定**：新增回归用例"移除条目后仍可绘制"。已验证该用例在回退修复时**确实崩溃**
（退出码 217），修复后通过。

### 4.2 起步页的样式分层误解（文档/模板层面）

引擎按主题**只加载一个**页面样式表（`main-<theme>.css`），不是在浅色之上叠加覆盖。
最初写的 `main-dark.css` 只覆盖颜色，导致深色档丢失布局（输入框塌成一条）。
修正为两个文件都是**完整样式表**（布局一一对应、只有颜色不同），并在模板注释与
工程 README 里写明，避免用户踩同一个坑。

### 4.3 诊断输出失败导致工具崩溃（用户实报）

**症状**：在 PowerShell 里运行已分发的 `lui-render-single.exe --init`（漏了目录参数），
除了参数错误提示，还跟着一句

```
Exception at 00000001000036B0: EInOutError:
Disk Full.
```

`lui-render-single.exe` 不带参数同样如此。磁盘显然没满。

**根因**：FPC 的 `WriteLn` 带 I/O 检查。目标句柄不可写时写操作失败，随后的 I/O 检查
抛出 `EInOutError`；FPC 把错误码 101 的固定文案当成了 "Disk Full"，于是这条与磁盘
毫无关系的误导性消息盖在了真正的诊断信息上。**关闭 stdout 句柄即可稳定复现**
（实测：普通 `WriteLn` 崩溃退 217，安全写退出码 2）。

**修复**：新增 `src/ui/xui_console.pas`，所有输出走 `ConWriteLn` / `ConErrWriteLn`：
用 `{$I-}` + `IOResult` 包住写入，失败不抛异常，并在首次失败后停止继续尝试
（后续写入必然同样失败，继续写只会反复触发）。诊断输出不该决定工具的成败。

### 4.4 同一次运行里两种编码混杂（用户实报的乱码）

**症状**：中文输出乱码（"浣跨敤 --help 鏌ョ湅鐢ㄦ硶"）。

**根因**（抓字节确认）：同一次运行的相邻两行输出，编码并不一致——

```
WriteLn('参数错误: ' + AMsg)     → GBK 字节（B2 CE CA FD …）
WriteLn('使用 --help 查看用法。')  → 原样 UTF-8 字节（E4 BD BF …）
```

**表达式**会经 RTL 按控制台码页转换，而**纯字面量被直写**（编译器把常量串直接交给
写例程，跳过转换）。于是同一屏里一半 GBK、一半 UTF-8，在 GBK 控制台上后半必然乱码；
某些宿主还因此写入失败，直接触发 4.3 的崩溃。

**修复**：不是在两种编码里挑一个，而是**让所有输出走同一条路径** —— `ConWriteLn`
的形参是运行时字符串，一律经 RTL 转换，从而与表达式输出同编码（跟随控制台码页）。
因此**不修改控制台码页**：RTL 本来就会对齐控制台码页，切码页反而引入新的"字节与码页
不匹配"，而且擅自改用户的终端状态也不合适（实测 cmd 下有无码页覆盖都能正确显示中文，
但只有统一路径能同时保证不乱码、不崩溃）。

### 4.5 `--json` 输出不是合法 JSON（三处，冒烟抓获）

`--json` 承诺"stdout 只含 JSON、日志走 stderr"（ADR 32），实际三处都破了：

| 缺陷 | 表现 | 修复 |
| --- | --- | --- |
| 日志混入 stdout | `[成功] 已渲染导出至…` 与 JSON 混排，`\| jq` 直接失败 | 新增 `LogLn`：`--json` 时人读日志一律走 stderr |
| 分隔符按输入下标算 | `--theme both` 下一条输入产出两个条目，中间条目丢逗号 → JSON 非法 | 改为按"已输出条目数"决定分隔符 |
| 路径未转义 | `JsonEscape` 写成 `StringReplace(S, '\\', '\\\\')`——Pascal 里 `'\\'` 是**两个**反斜杠，于是只在出现连续两个 `\` 时才替换；Windows 绝对路径 `E:\codes\…` 原样入 JSON，`\c` 不是合法转义 | 按单字符逐个转义（含引号与控制字符） |

第三条尤其隐蔽：相对路径（无 `\`）测不出问题，只有绝对路径才暴露。这三条现在都由
`npm run pack` 的 `--json` 冒烟与 runtests 相关断言守住。

### 4.6 选项缺值被当成值：`--init --force` 建出叫 `--force` 的目录

`NeedValue` 只检查"还有没有参数"，不检查下一个参数长什么样。于是 `--init --force`
把 `--force` 当成目录名，**真的建出一个名为 `--force` 的目录**并生成工程，用户看到
"命令成功了但什么都没生成对"。修复：下一个参数若以 `-` 开头（且不是单独的 `-`）即判
缺值。已加入 pack 冒烟。

## 5. ADR（续 M10，编号 41 起）

| ADR | 决策 | 理由与代价 |
| --- | --- | --- |
| 41 | **渲染器承担项目工具链入口**（`--init` / `--check` / `--pack`），而不是另起一个 CLI 程序 | 一个 exe 走完生命周期，分发与文档都只有一份；工具链逻辑能复用引擎的装配与资源发现。代价：渲染器职责变宽（用模式分派与独立单元 `xui_scaffold.pas` 隔离） |
| 42 | **生成即自包含**：模板同级 `ui/` 整树复制进新工程 | 工程可脱离 lui 仓库独立提交与交付；单程序版也能生成完整工程。代价：每工程多约 100 KB 运行时（值得） |
| 43 | **`--init` 只写不改不删**；非 lui 工程的非空目录拒绝写入 | 脚手架最怕的就是吃掉用户文件；"跳过已存在"也让重跑可用来补新增文件。代价：覆盖需显式 `--force` |
| 44 | **模板定位单一实现**（`xui_scaffold.XuiScaffoldDir`）：当前目录向上 → exe 目录向上 → 内嵌解包根 | 仓库内开发、打包分发、单程序版三种形态共用一条查找链，与 `xui_app.FindRepoRoot` 同构。代价：查找链要保持与分发布局同步（由冒烟覆盖） |
| 45 | **`.cmd` 模板纯 ASCII**，中文只在渲染器运行时输出 | `cmd.exe` 用 OEM 码页解码批处理，非 ASCII 会乱码甚至被误当命令执行（实测）。代价：脚本注释用英文 |
| 46 | **`--check` 退出码即门禁**（有脚本错误退 1），与 `--json` 分离（日志走 stderr） | 让"页面能跑"进入 CI，而不是靠肉眼看图；JSON 可解析。代价：自检跑一遍完整装配（每页约 0.2s，可接受） |
| 47 | **所有控制台输出走统一安全路径**（`xui_console`）：写失败不抛异常、编码一致 | FPC 把"写失败"误报成 "Disk Full" 并崩溃，而"字面量直写 / 表达式转码"的混杂会让中文乱码；统一路径一次解决两者。代价：多一个薄单元、输出调用要记得用它（由 pack 冒烟与 runtests 守） |

## 6. 文件清单

## 8. 已知限制

- `.cmd` 脚本是 Windows 形态；POSIX 需要时补 `.sh`（渲染器本身跨平台可构建）。
- `run-test.cmd` 逐个页面串行自检，页数很多时线性耗时（每页约 0.2s）。
- `--check` 只覆盖"装配 + 首屏 + 脚本错误"，不模拟交互（交互正确性由工程自己写用例，
  或参考 `tests/runtests.lpr` 的引擎级用例）。
- 起步页用固定视口与显式行列，未用 `flex: 1` 之外的弹性布局：引擎 flex 子集无 `wrap`/`shrink`，
  自适应布局能力有限（见工程 README 的不支持清单）。
- `--pack` 的资产收集覆盖页面同目录的 `assets/`；页面若引用更远的相对路径，需手工补齐。
