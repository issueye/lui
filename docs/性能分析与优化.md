# 性能分析与优化记录

对引擎做过两轮热点剖析与优化（均为 2026-09）。剖析工具为 lui-render 的
`--bench N`：渲染成功后对同一文档重复 N 次「样式级联 + 布局 + 绘制」完整重排
（`InvalidateStyles` + `Draw`，与 GUI 稳态失效重算同路径）并输出耗时。

- 页面：`demo/stress.xml`（600 节点，混合 class 与内联样式，含文本断行）
- 命令：`lui-render demo/stress.xml -o out.png --bench 20`（默认视口 800×600）
- 本机耗时波动约 ±10%，下表取多次运行的代表值

## 总结

| 轮次 | 手段 | 完整重排（stress 页） |
| --- | --- | --- |
| 起点 | — | ≈ 114.9 ms/次 |
| 第一轮 | 文本测量 memo + 内联样式解析缓存 | ≈ 77 ms/次（-33%） |
| 第二轮 | CSS 规则索引 + 渲染器缓存体系（详见下） | **≈ 9.4 ms/次（累计 -92%）** |

第二轮前后在其余演示页（`--bench 20`，560×980）的实测：

| --- | --- | --- | --- |
| stress | 73.4 | 9.4 | 7.9x |
| ui_gallery | 28.1 | 11.7 | 2.4x |
| agent | 8.6 | 3.9 | 2.2x |
| m7 | 10.2 | 5.5 | 1.9x |
| ui | 14.1 | 7.8 | 1.8x |
| todo | 7.1 | 3.9 | 1.8x |
| list | 6.3 | 3.9 | 1.6x |
| login | 4.7 | 3.1 | 1.5x |

所有页面渲染结果**逐像素不变**（PNG 字节一致）；`runtests` 715 项全绿。

## 第一轮（2026-09 上旬）

热点结论：

1. **文本测量占重排 50% 以上**：断行布局对同一段文本反复调用
   `MeasureText`（前缀/逐词度量），同字体签名下大量重复计算。
2. CSS 级联与内联样式解析、声明排序在此规模下为噪声级开销。
3. 字体**句柄**缓存（保持 HFONT 存活复用）在本机实测为**负收益**
   （GDI 内部字体缓存对持续存活的多个逻辑字体表现不佳），
   逐次 `CreateFontW`/`DeleteObject` 反而更快——已放弃该方案。

已落地：

| 优化 | 位置 | 效果 |
| --- | --- | --- |
| 文本测量结果 memo（`family|size|bold|text` → 宽高，上限 16384 条） | `TGdiPlusRenderer.MeasureText` | 完整重排 114.9 → ≈75 ms/次 |
| 级联声明排序冒泡 → 插入排序 | `xui_css_match.ComputeNodeStyles` | 小数组上更快更简单 |
| 内联 `style` 解析缓存（挂在 `TXuiNode.InlineStyleCache`，按属性原文失效） | `xui_css_match` + `xui_dom` | 全树重算时免逐节点重复解析 |
| `--bench N` 基准模式 | `lui_render` | 性能回归可量化 |

## 第二轮（2026-09 中旬）

第一轮的剖析工具只给了整体耗时，这一轮先做**分阶段计时插桩**（临时给
级联/布局/绘制/测量各阶段挂计时器，测完移除），才看清真实分布——
与第一轮的估计完全不同：

| 阶段 | 优化前（ms/帧） | 占比 |
| --- | --- | --- |
| 样式级联 | 58.8 | 76% |
| ├ 选择器匹配 | 55.4 | 71% |
| ├ 默认样式构建（含变量表继承） | 1.3 | 2% |
| └ 规则索引/声明应用/释放 | 2.1 | 3% |
| 布局 | 3.7 | 5% |
| ├ 文本断行 | 3.6 | 5% |
| 绘制 | 16.2 | 21% |
| ├ 文本（字体对象 + GDI+ 排版 + 绘制） | 15.3 | 20% |
| └ 填充/描边/绘制序 | 0.9 | 1% |

关键结论：**选择器匹配是绝对热点**（603 节点 × 263 条规则 = 每帧 15.9 万次
`MatchSelector`），而第一轮以为的"少量规则"实际来自组件库主题
（`ui/theme/lui-light.css` 单文件 255 条规则）。文本测量经第一轮 memo 后
已不是主要矛盾。

### 已落地

| 优化 | 位置 | 效果 |
| --- | --- | --- |
| **CSS 规则索引**：按右端复合选择器的选择键（`#id` / `.class` / `tag`）分桶，逐节点只对候选规则做匹配；桶内保持 (表序, 规则序)，级联顺序不变 | `xui_css_match.TCssRuleIndex` | 完整重排 78.2 → **25.0 ms/次（-68%）**，选择器匹配 55.4 → 1.9 ms/帧 |
| **GDI+ 字体对象缓存**：`family|size|bold` → 字体族 + 字体对象（上限 64 条），regular/bold 交替不再逐次创建销毁 | `TGdiPlusRenderer.EnsureFont` | 25.0 → **16.4 ms/次**（-34%） |
| **DrawText 行高 memo**：垂直居中所需的 GDI+ 排版行高按 (字体, hint, 布局高, 文本) 记忆，省去逐次 `GdipMeasureString` | `TGdiPlusRenderer.GpSlotFor` | 文本绘制 7.9 → 1.0 ms/帧 |
| **测量 memo 改直接映射表**：`MeasureText` 不再拼 `family|size|bold|text` 长 key、不做 locale 比较，签名 + 文本 → 宽高（4096 槽，冲突即重算） | `TGdiPlusRenderer.MeasureText` | 断行 3.6 → 1.6 ms/帧 |
| **索引桶用非 locale 比较**：自建 `TCssKeyList` 覆写 `CompareStrings`（`CompareStr`/`CompareText`），避开 `AnsiCompareText` | `xui_css_match` | 索引构建 1.04 → 0.83 ms/帧 |
| **`HasClass` 去 locale 比较**：先逐字节 `CompareText`，仅当类名含非 ASCII 字节才回退到原 `ClassList.IndexOf`，语义不变 | `xui_dom.HasClass` | 选择器匹配再 -27% |
| **字体查找一级短缓存**：样式 → 字体对象（4 条线性命中），命中即免字体族解析与 key 拼接 | `TGdiPlusRenderer` | 字体查找 0.88 → 0.05 ms/帧 |
| **文本渲染质量状态缓存 + UTF-16 文本复用**：hint 未变化时不重复调 `GdipSetTextRenderingHint`；UTF-16 转换结果随行高 memo 槽缓存 | `TGdiPlusRenderer.DrawText` | 文本绘制 2.9 → 2.5 ms/帧 |

### 过程中的一个坑（记录备查）

字体签名的一级短缓存最初用 `Move` 在环形槽位间搬移记录以维持 LRU 顺序。
记录里含托管字符串字段，`Move` 是裸内存拷贝、不维护引用计数：搬移后旧槽被
新值覆盖时引用计数减到 0，**字符串被提前释放**，仍指向它的槽位随即悬空——
表现为组件库页面（字体签名超过 4 种）访问冲突崩溃，而只有 2~3 种签名的
页面完全正常。改为**环形写入、不做记录搬移**后修复。
教训：含托管字段的记录不要用 `Move` 做搬移，要么用记录赋值（编译器维护
引用计数），要么改成环形索引。

## 后续可选

- **级联样式对象重建**仍是样式阶段主要开销（≈1.2 ms/帧 @600 节点）：
  每帧为每个节点 `DefaultStyleForTag` 新建样式并 `Vars.Assign` 继承变量表，
  再释放旧对象。可行方向是按 (父样式对象, tag, id, class, 伪类, 内联 style,
  样式表版本) 做签名复用，但需要严格的失效纪律（样式表变更、脚本改 class
  / style / 伪类都必须命中失效点），风险明显高于收益，暂不做。
- 规则索引目前**每帧重建**（≈0.8 ms/帧）：可改为引擎持有 + 在样式表变更点位
  显式失效；注意索引持有规则对象引用，热重载重解析后必须重建，否则悬空。
- 桶内下标数组逐条 `SetLength` 增长：可改两遍（计数 → 填充）省掉重分配。
- 布局断行仍逐词度量（≈1.6 ms/帧）：可记录逐词宽度增量减少测量次数。
- `TGdiRenderer`（非 Windows / 降级路径）未加测量 memo。
- 脚本引擎对象属性查找（`FindOwn` 线性扫）：在对象属性数大时换哈希；
  常规 UI 脚本对象属性少，暂不动。

## 时间线基准（R4 决策依据，2026-09-16）

**动机**：lui 的布局是整树重排（`LayoutDocument` 从根开始），会话时间线随消息增长会持续变慢。
为判断是否需要列表虚拟化，先做可复现的测量，而不是凭感觉优化。

**工具**：`npm run bench:timeline`（`scripts/bench-timeline.js`）生成对齐 a_da 时间线结构的页面
（`x-for` 渲染消息，每条 1 容器 + 3 文本节点：角色 / 正文（中文约 50 字，会换行）/ 工具行），
并调用渲染器 `--bench`。渲染器新增 `--bench-mode full|layout|paint` 以分离失效级别：

- `full`：整树样式重算（级联 + 继承）+ 布局 + 绘制（最坏情况，例如换肤）；
- `layout`：仅布局 + 绘制（新增节点、文本变化、尺寸变化）；
- `paint`：仅绘制（纯重绘）。

**结果**（560×900，`--bench 30`，Windows x64，GDI+ 后端，单位 ms/次）：

| 消息数 | full（级联+布局+绘制） | layout（布局+绘制） | paint（仅绘制） |
| --- | --- | --- | --- |
| 20 | 13.03 | 5.73 | 2.60 |
| 50 | 27.60 | 11.97 | 4.70 |
| 100 | 51.03 | 21.37 | 7.83 |
| 200 | 99.47 | 39.07 | 13.03 |
| 400 | 194.80 | 76.03 | 24.47 |

**结论**：

1. 耗时随节点数近似线性（约 0.48 / 0.19 / 0.06 ms 每条消息），说明成本来自逐节点遍历而非某处
   意外复杂度；没有"某个数量级突然劣化"的断点。
2. **绘制便宜、布局主导**：100 条消息时仅绘制 7.8 ms（仍在 60fps 预算内），但仅布局+绘制已 21.4 ms
   （超出预算），整树级联 51 ms（换肤等全局失效场景）。
3. 因此"列表很长时卡"的根因是**整树布局**，而不是绘制吞吐；单纯减少重绘（缓存位图）收益有限。
4. 应对策略：
   - **应用层窗口化（推荐，先做）**：时间线只渲染最近 N 条消息（约 60 条）+ "显示更早的消息"
     分页加载，把节点数稳定在可控范围；不需要引擎改动，今天就能用 `x-for` 配合数组切片实现；
   - **引擎级增量布局/虚拟化（后置）**：让布局从脏子树开始、窗口外节点不参与布局；这是引擎
     改动，收益随消息数增长而放大，但风险与工作量都显著更高，需独立立项。

**回归守护**：`npm test` 现有 801 项不受影响；基准脚本属测量工具，不进入断言路径。

## R8：级联规则索引与断行缓存（2026-09-17）

同一台机器、同一基准命令，改动前后各测 30 帧；**渲染结果按字节校验完全一致**
（`demo/stress.xml` 前后 PNG md5 相同，说明只是变快、没有改变语义）。

### 目标 1：样式级联的规则匹配（stress 页主导成本）

实测分解（`demo/stress.xml`，1280×800，30 帧）：

| 级别 | 改动前 | 改动后 |
| --- | --- | --- |
| `--bench-mode full` | 2438 ms（81.3 ms/帧） | 750 ms（25.0 ms/帧） |
| `--bench-mode layout`（布局+绘制） | 672 ms（22.4 ms/帧） | 657 ms（21.9 ms/帧） |
| `--bench-mode paint`（仅绘制） | 578 ms（19.3 ms/帧） | 563 ms（18.8 ms/帧） |

改动前 full − layout ≈ **59 ms/帧**全部花在级联上（占整帧 72%）；改动后该差值约 3 ms/帧。

原因：原实现对每个节点遍历「全部样式表 × 全部规则 × MatchSelector」，
是 O(节点×规则)。做法：按选择器**最右简单选择器**的 id/class/tag 建索引分桶
（`TCssRuleIndex`）。选择器要匹配某节点，其最右 part 必须匹配该节点自身，因此候选集 =
通用桶 + 该节点的 id/class/tag 桶；候选仍需 `MatchSelector` 复核，且用跨样式表全局序
（`TCssRule.GlobalOrder`）排序，保证同特异性时的胜出顺序与全量遍历完全一致。

### 目标 2：文本断行结果缓存（长列表页主导成本）

时间线基准（`node scripts/bench-timeline.js`，560×900，30 帧）：

| 消息数 | full 前 → 后 | layout 前 → 后 | paint |
| --- | --- | --- | --- |
| 50 | 14.07 → **8.33 ms** | 11.97 → 5.20 ms | 5.20 ms |
| 100 | 25.50 → **12.50 ms** | 23.97 → 9.37 ms | 7.30 ms |
| 200 | 46.90 → **21.37 ms** | 41.13 → 16.13 ms | 13.53 ms |
| 400 | — → **39.57 ms** | — → 28.63 ms | 24.50 ms |

原因：每帧对每个静态文本重新 `SplitUnits` + 逐单元测量。做法：在 `xui_text` 内加断行结果
缓存，键包含**全部影响断行的输入**——文本、字体族/字号/粗体、`letter-spacing`、
`white-space`、`text-overflow`、可用宽度（0.5px 量化）、测量器实例身份（方法代码 + 对象）
与显式 epoch；只缓存行、不缓存高度（高度按调用时的 `line-height` 推导），避免"改了样式却
命中旧值"。缓存上限 768 条，超限整体清空；`InvalidateWrapCache` 供热重载/测试显式失效。

### 顺带修掉的四个正确性缺陷（都由新回归或应用实测暴露）

1. **缓存键大小写不敏感会串命中**：`TStringList` 默认 `CaseSensitive=False`，键里含原文时
   `abc` 会命中 `AbC`。已显式 `CaseSensitive := True`。
2. **`letter-spacing` 未计入断行宽度**：逐单元累加行宽时漏算了单元之间的字距（渲染器逐字
   推进字距），带字距的文本会溢出容器。已在累加时计入。
3. **`letter-spacing` 只在 GDI 后端实现**：应用默认走 GDI+（`xbAuto`），于是"测量/绘制不含
   字距、断行却算字距"，带字距的标签被提前折行。已在 GDI+ 的 `MeasureText`/`DrawText` 实现
   同口径字距（并把字距加入其测量 memo 键），两套后端的字距公式统一为
   `Round(字距 × (字数-1))`。
4. **分配口径与断行口径不一致**：盒子宽度由「整串测量」（max-content）分配，而断行按「逐单元
   累加 + 字距」，逐段测量/取整之和可能略大于整串值，于是"明明放得下却被折行"。现在断行先做
   一次整串判断：整串放得下即单行（与分配口径一致），只有真正放不下才进入逐单元折行，且比较
   按整像素取整。

其中 3、4 由 a_da 界面实测发现（带字距的小标签折行），并在 a_da 侧以截图核对修复效果。
