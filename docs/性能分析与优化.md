# 性能分析与优化记录

对引擎做了一次热点剖析与优化（2026-09）。剖析工具为 lui-render 新增的
`--bench N`：渲染成功后对同一文档重复 N 次「样式级联 + 布局 + 绘制」完整重排
（`InvalidateStyles` + `Draw`，与 GUI 稳态失效重算同路径）并输出耗时。

## 基准方法与基线

- 页面：`demo/stress.xml`（600 节点，混合 class 与内联样式，含文本断行）
- 命令：`lui-render demo/stress.xml -o out.png --bench 20`
- 基线：完整重排 ≈ **114.9 ms/次**；其中文本测量约 2272 次/次重排

## 热点结论（按实测影响排序）

1. **文本测量占重排 50% 以上**：断行布局对同一段文本反复调用
   `MeasureText`（前缀/逐词度量），同字体签名下大量重复计算。
2. CSS 级联与内联样式解析、声明排序在此规模（600 节点 × 少量规则）下
   均为噪声级开销。
3. 字体**句柄**缓存（保持 HFONT 存活复用）在本机实测为**负收益**
   （GDI 内部字体缓存对持续存活的多个逻辑字体表现不佳），
   逐次 `CreateFontW`/`DeleteObject` 反而更快——已放弃该方案。

## 已落地

| 优化 | 位置 | 效果 |
| --- | --- | --- |
| 文本测量结果 memo（`family|size|bold|text` → 宽高，上限 16384 条） | `TGdiPlusRenderer.MeasureText` | 完整重排 114.9 → **≈75 ms/次（约 -35%）**；测量是纯函数，结果与逐次调用完全一致 |
| 级联声明排序冒泡 → 插入排序 | `xui_css_match.ComputeNodeStyles` | 小数组上更快更简单 |
| 内联 `style` 解析缓存（挂在 `TXuiNode.InlineStyleCache`，按属性原文失效） | `xui_css_match` + `xui_dom` | 全树重算时免逐节点重复解析 |
| `--bench N` 基准模式 | `lui_render` | 性能回归可量化 |

验证：`runtests` 633 项全绿；stress 页渲染结果像素不变。

## 后续可选

- `TGdiRenderer`（非 Windows / 降级路径）加同样的测量 memo。
- 布局断行算法：减少重复度量次数（记录逐词宽度增量），从源头降低测量调用量。
- CSS 规则按右端 tag/class 建索引桶：仅在规则数量大（数百+）时有意义，
  当前规模实测无收益，暂不做。
- 脚本引擎对象属性查找（`FindOwn` 线性扫）：在对象属性数大时换哈希；
  常规 UI 脚本对象属性少，暂不动。
